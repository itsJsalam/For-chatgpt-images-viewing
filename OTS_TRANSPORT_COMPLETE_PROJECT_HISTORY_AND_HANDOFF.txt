================================================================================

A. Separate apps
- Public passenger/driver app and private admin app must be separate.
- Never expose an admin menu, admin login option or admin access path in the public app.
- Hiding an admin button is not security. Admin operations must verify server-side admin authorization.
- Admin access is for the owner or specifically selected trusted people, not arbitrary users.

B. One driver account, one registered car
- Current decision: one driver registers one vehicle. Do not implement multiple vehicles per driver unless the user explicitly changes this later.
- A driver must be approved by an administrator before publishing trips.
- Review changes to identity/vehicle details. Critical edits should trigger re-review if the database/business rules support it; verify actual enforcement before claiming it.

C. Exactly five seats in a standard car
The user repeated this correction and explicitly said it is important:
- Five seats total in the car.
- One seat for the driver, never bookable.
- One front passenger seat, bookable.
- Three rear passenger seats, bookable.
- Maximum four passengers.
- Seat 1 = front passenger; Seats 2, 3 and 4 = rear passengers.
- Do not count the driver seat in passenger capacity.
- Selected seat labels, passenger count, database capacity and the visual car must agree.
- A specific approved vehicle may have fewer passenger seats, but the standard maximum is four. Do not silently change existing live vehicle records.

D. Trip and booking correctness
- Only approved drivers can publish.
- Show origin, destination, departure time, estimated arrival when available, fare, available passenger seats, driver details and vehicle information.
- Prevent double booking at the database level, not merely by disabling a button in the UI.
- A temporary seat-hold countdown must correspond to a real server-side expiry; a decorative timer is unacceptable.
- If a transfer is submitted and waiting for admin review, do not release the seat just because a timer expires before the admin checks the transfer. Use a clearly defined policy.
- Expired unpaid holds without pending transfer submissions should release seats safely.
- Confirmed bookings must not lose seats due to a stale client timer.
- Cancellation, accidental seat selection and booking status need clear user-facing flows.

E. Visual design

- User reported installing an APK and seeing no visible change. This is a serious release communication failure; future APK links must identify exact commit and workflow run.

- Use the supplied OTS logo “for now.”

F. Cost controls

Intended manual workflow:
1. Passenger selects seat(s).
2. Server creates a pending-payment booking and a time-limited seat hold.
3. App shows chosen wallet method, amount, account destination (after owner confirms), instructions and transaction reference input.
4. Passenger transfers money in the real wallet app.
5. Passenger submits a reference. This is only a claim, not proof money arrived.
6. Admin app displays the submission with amount, method, reference, passenger/trip context and status.
7. Admin checks the actual wallet transaction and verifies or rejects.
8. Verification confirms the booking; rejection cancels/releases it.
9. Expired holds without a pending transfer should be released. Submitted transfers awaiting review should not be auto-cancelled prematurely.
10. Audit the decision and show clear passenger-facing status.

Source/database groundwork reported in recent work:
- Admin API model/query for payment submissions and RPC review call.
- Admin “Payments” screen with manual verify/reject controls.
- SQL functions for payment review and expired-hold cleanup.
- Passenger booking model reads payment submission status/method.
- Booking history can offer “Continue payment” for a pending booking with no submitted reference.
- Seat-selection trigger/function intended to enforce passenger count, allowed seat labels, duplicate labels and overlapping active bookings.
- Ticket wording was changed to “DIGITAL BOOKING TICKET” and explains that the QR is a booking reference, not an independently verified boarding pass.

Important limitations:
- This is not an automatic wallet integration. Manual admin verification is required.
- The latest admin build must be verified after payment UI edits. The known successful admin build below predates some payment changes.
- Check SQL grants, RLS, foreign-key relationships used by PostgREST nested reads, admin RPC authorization and race conditions.
- Payment review function was changed to SECURITY INVOKER and intended to restrict execute to authenticated users, while checking private.is_active_admin(). Confirm actual effective grants and RLS.
