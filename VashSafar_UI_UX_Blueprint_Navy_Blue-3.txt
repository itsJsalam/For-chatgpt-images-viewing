======================================================================
0. PURPOSE, SCOPE, AND STATUS
======================================================================

This document captures the currently discussed UI/UX requirements for Vashسفر, the Android application used by passengers and drivers.

PRODUCTS MUST REMAIN SEPARATE:
1. Vashسفر — Passenger and Driver Android app. This document specifies its UI.
2. Vashsafar Admin — Separate operations Android app. It does NOT inherit the special low-literacy, voice-first design requirements in this document.
3. Silent Owner website — Separate private website with its own advanced security-focused design. It does NOT inherit the passenger/driver visual layout in this document.

The user's explicit design preference is a NAVY BLUE UI, with an illustrated, tile-based style inspired by the supplied Easypaisa screenshots:
- Large rounded cards.
- A 3D-style illustration centered in each card.
- A short option label beneath the illustration.
- Tapping a card opens a clear next-step selection panel or screen.
- A clean, consistent visual language.
- Easy use for passengers and drivers, including users with limited literacy or smartphone experience.

This is a requirements/planning document. It does not claim any feature is already implemented. Design values are proposals and can be adjusted before development. Existing business rules and server-side validation remain authoritative.

======================================================================
1. CORE PRODUCT PRINCIPLES
======================================================================

1.1 Passenger and driver usability
- Essential tasks must not depend entirely on the user's ability to read.
- Use recognizable illustrations, short labels, clear touch targets, optional spoken guidance, and step-by-step flows.
- Support English and Urdu throughout relevant screens.
- Urdu must use correct right-to-left (RTL) layout and appropriate typography.
- Users can complete all essential tasks by tapping; voice is optional, never mandatory.
- Minimize typing and avoid complicated forms.
- Provide clear success, pending, failed, and unavailable states.
- Keep navigation consistent.
- Do not make the interface childish; it should feel trustworthy, premium, calm, and respectful.

1.2 Visual reference
The Easypaisa screenshots supplied by the user are references for the interaction pattern, not for copying its brand:
- Large tile/card with illustration and label.
- Home screen with prominent service options.
- Tap an option to open a modal/bottom sheet with selectable choices.
- Use a similar sense of simplicity, spacing, and discoverability.
Do not copy Easypaisa logos, icons, proprietary illustrations, or exact branding.

1.3 Safety and truthfulness
- Only show journeys that are configured and available for the selected date and route.
- Never invent a fare, schedule, arrival time, available seat, payment success, or confirmed ticket.
- Fare, inventory, booking, payment, permissions, freeze enforcement, and ticket validity are validated by the backend.
- A visual state alone must never be treated as proof of payment or booking.
- Emergency features should remain accessible when technically possible.
- Do not encourage drivers to interact with the phone while moving.

2. NAVY BLUE VISUAL DESIGN SYSTEM
======================================================================

2.1 Proposed color palette
These are proposed design tokens, not yet final brand decisions.

- Primary Navy: #102A43
  Use: main brand surfaces, selected navigation, primary headers, key actions.
- Deep Navy: #071A2D
  Use: top bars, high-emphasis areas, dark text on light cards where suitable.
- Secondary Blue: #1F4E79
  Use: secondary buttons, illustration details, selected chips.
- Light Blue: #D9EAF7
  Use: pale blue card backgrounds, subtle highlighted areas.
- Page Background: #F4F7FA
  Use: default light page background.
- Card White: #FFFFFF
  Use: cards, selection panels, forms.
- Text Primary: #172B4D
  Use: main readable text.
- Text Secondary: #526579
  Use: supporting text.
- Success Green: #16865C
  Use: confirmed/success state, not as the primary brand color.
- Warning Amber: #F2B84B
  Use: attention warnings, pending notices.
- Error Red: #C93636
  Use: errors, cancellations, danger actions.
- Border: #D9E2EC
  Use: separators and card borders.

2.2 Color rules
- Navy blue is the main identity color across Vashسفر.
- Use white or very light backgrounds behind most content for readability.
- Do not use navy text on dark navy surfaces without sufficient contrast.
- Never communicate state using color alone; add an icon and a text/voice label.
- Do not use bright red for ordinary actions. Reserve it for errors, destructive actions, or urgent danger.
- Selected cards should have a clear navy border or highlight and a check indicator.
- Dark mode may be considered later, but the first visual system should be designed and tested in a clear light theme with navy accents.

2.3 Illustrations
- Use polished 3D-style illustrations for provinces/regions, cities, cars, buses, tickets, help, and settings. Do not add a luggage-selection or luggage-fee feature.
- Keep illustrations consistent in lighting, perspective, stroke/detail, and scale.
- Illustrations must reinforce the label rather than replace it.
- Every image card also needs a text label and accessible spoken label.
- Avoid excessive animation that slows low-end phones or consumes data.
- Prefer optimized local assets for common illustrations; load optional photographs only when needed.
- Use licensed/original assets; do not copy Easypaisa brand artwork.

2.4 Typography
- Use a highly legible Android font pairing suitable for English and Urdu.
- Urdu must render correctly, including connected glyphs and RTL punctuation/layout.
- Main titles: large and clear.
- Button labels: short, high contrast, never clipped.
- Avoid long all-capital labels.
- Support larger text settings without breaking card layouts.
- Use simple everyday wording, not technical jargon.

2.5 Shape, spacing, and touch targets
- Cards: rounded corners, consistent radius (proposed 18–24 dp).
- Buttons: rounded corners, strong contrast, clear pressed/disabled states.
- Use comfortable spacing between tappable items.
- Aim for at least 48 dp touch targets; larger is preferable for primary actions.
- Keep bottom navigation labels readable.
- Avoid tiny icon-only actions for essential tasks.
- Use subtle elevation/shadow only where it improves hierarchy; do not make the screen visually noisy.

3. APP ROLES AND MODE SEPARATION
======================================================================

Vashسفر supports passengers and drivers in one Android app, but their experiences differ.

Passenger mode:
- Journey search and booking.
- Ticket access.
- Trip information.
- Support and emergency help.
- Personal settings.

Driver mode:
- Assigned trips.
- Departure and trip status.
- Passenger/seat manifest as authorized.
- Route and stop information.
- Support, breakdown help, SOS.
- Driver account and preferences.

Rules:
- Show a clear role-specific interface after authentication.
- Do not mix driver controls into passenger navigation.
- Do not let a user accidentally switch into a privileged driver interface without proper account authorization.
- Driver approval and document status are enforced server-side.
- The app must not offer driver trip publishing or booking acceptance if the driver is not approved or is suspended/blocked.
- This document does not define Vashsafar Admin or Silent Owner website navigation.

4. PASSENGER BOTTOM NAVIGATION — FIVE BUTTONS
======================================================================

Persistent passenger bottom navigation (except full-screen flows such as QR scanning where hiding it is useful):

1. HOME
Icon: simple house.
Label: Home / Urdu equivalent.
Tap behavior:
- Return to passenger home screen.
- If the user has an unfinished booking, show a small “Continue booking” card rather than silently discarding their work.
- Do not reset an existing selection without warning.

2. MY TRIPS
Icon: route/road with a small ticket or calendar.
Label: My Trips.
Tap behavior:
- Open trip-management screen with tabs: Upcoming, Completed, Cancelled.
- Upcoming: confirmed future trips and relevant boarding reminders.
- Completed: finished journeys.
- Cancelled: cancelled journeys and refund state.
- Each trip card opens View Trip.
- Cancellation action is shown only when permitted; display refund amount and policy before final confirmation.

3. MY TICKETS
Icon: ticket with QR motif.
Label: My Tickets.
Tap behavior:
- Open a list of confirmed tickets.
- Provide prominent access to the QR code and booking reference.
- Pending bookings must be visibly marked Pending and must not look like confirmed tickets.
- If there are no tickets, show a helpful empty state and a Book a Journey button.
Difference from My Trips:
- My Trips is for managing a journey.
- My Tickets is for quickly retrieving the actual ticket and QR code.

4. HELP
Icon: headset or life ring.
Label: Help.
Tap behavior:
- Open help categories and contact options.
- Emergency/SOS must be visually separate from ordinary customer support.
- Do not display an unverified support phone number.
- Call/chat channels appear only when configured and available.

5. SETTINGS
Icon: gear.
Label: Settings.
Tap behavior:
- Open language, voice, notifications, account, security, accessibility, privacy, payment preferences, about, and sign-out sections as supported.
- Do not expose administrative or Silent Owner controls here.

Navigation behavior:
- Highlight the active destination with navy styling and a clear selected indicator.
- Use icon + text, never icon alone.
- Support English and Urdu labels.
- For Urdu RTL, mirror navigation placement appropriately while preserving expected Android navigation behavior.
- Bottom navigation remains visible on ordinary main screens; hide it only when a full-screen task benefits from it (e.g., QR scanner or a focused confirmation screen).
- Preserve form/booking progress when moving between tabs where feasible.

5. PASSENGER HOME SCREEN — SCREEN-BY-SCREEN BLUEPRINT
======================================================================

Purpose: Let the passenger start a booking quickly and understand the next step.

5.1 Top app bar
Elements:
- Vashسفر logo/wordmark at the start of the bar.
- Optional greeting (for example, “Where would you like to go?”).
- Notifications bell at the opposite end.
- Optional profile/avatar only if useful; do not crowd the header.

Button behavior:
- Logo/Home: returns to home.
- Notifications bell: opens notifications list; unread count is shown only when there are unread items.
- Profile/avatar if present: opens account/profile details, not a hidden admin menu.

5.2 Main “Book a Journey” card
Appearance:
- Large navy-accented rounded card.
- Premium 3D transport/road illustration.
- Strong title: “Book a Journey”.
- One short supporting line, optionally read aloud.
- Entire card is tappable, with a clear press state.

Tap behavior:
- Start the agreed journey flow at Province/Region selection.
- If a draft booking already exists, offer “Continue” or “Start a new search”.
- Starting a new search must not silently delete a held seat or confirmed booking.

5.3 Quick action cards
Use an illustrated card grid, inspired by the supplied Easypaisa pattern.

Suggested cards:
A. Cars
- Car illustration, label “Cars”.
- Tap starts a booking flow and selects Cars as the preferred vehicle type, while still collecting the province, city, and travel date if missing.

B. Buses
- Bus illustration, label “Buses”.
- Tap starts a booking flow and selects Buses as the preferred vehicle type, while still collecting the province, city, and travel date if missing.

C. My Tickets
- Ticket/QR illustration.
- Tap opens My Tickets.

D. Help & Support
- Headset illustration.
- Tap opens Help.

These cards must not create a second conflicting booking flow. They are shortcuts into the same validated journey-search process.

5.4 Upcoming journey card
Shown only when the passenger has a relevant upcoming booking.
Content:
- Origin and destination.
- Date and departure time.
- Boarding point.
- Booking status.
- “View Trip” button.
- Boarding reminder if appropriate.
Do not show private details on a lock screen notification without user consent.

5.5 Announcements
- Show only important, relevant, authorized service announcements.
- Avoid advertising clutter.
- Tapping an announcement opens its full details.
- Label urgent service disruption clearly and truthfully.

5.6 Voice assistance control
- Optional speaker/microphone control with a clear label.
- Speaker action reads the screen's main instruction aloud.
- Repeat button replays the current instruction.
- Voice search may accept a spoken destination, but always provide manual selection if recognition fails.
- Explain microphone permission when requesting it.
- Never require voice input to complete booking.

5.7 Home screen empty/error states
- No upcoming trips: show “No upcoming trips” plus Book a Journey.
- Offline: show a clear offline notice; do not pretend live seat availability is current.
- Loading: show a simple loading indicator and accessible text.
- Error: explain what failed and provide Retry.
- No notifications: show a simple empty state.

6. JOURNEY SEARCH FLOW — PROVINCE, CITY, VEHICLE, DATE, RESULTS
======================================================================

MANDATORY ORDER REQUESTED BY USER:
1. Province/region.
2. City.
3. Cars or Buses.
4. Travel date (collect before final available-journey results).
5. List all matching available cars or buses.
6. Show fares, scheduled departure time, estimated arrival time, and availability.
7. Select seats and continue booking.

Quetta is the central origin hub for this product direction. The system should support destinations throughout Pakistan where a real, configured Quetta service exists. Return journeys from other cities to Quetta may be shown only where return services are configured and available.

Do not list every city in Pakistan indiscriminately. Only list cities with a configured route/service from Quetta, and filter final results by actual service on the chosen date.

6.1 Screen: Province / Region selection
Header:
- Back button.
- Title: “Where do you want to go?”
- Optional speaker/repeat instruction control.
- Progress indicator such as “Step 1 of 5”.

Layout:
- Illustrated cards in a responsive grid or vertically scrolling list.
- Each card includes a 3D-style regional illustration, the name, and an optional chevron.
- Names should be shown in the selected language; bilingual names can be used where space permits.
- Large touch target and clear selected state.

Possible administrative categories:
- Balochistan
- Punjab
- Sindh
- Khyber Pakhtunkhwa (KPK)
- Gilgit-Baltistan
- Azad Jammu & Kashmir
- Islamabad Capital Territory (shown as a territory, not a province)

Important geographic classification:
- Karachi is a city in Sindh, not a province.
- Islamabad is the Islamabad Capital Territory, not a province.
- Categories and names must be verified before production and must not imply that every region has an active route.

Tap behavior:
- Tapping a region opens the City selection screen.
- Only show region options that contain at least one configured destination from Quetta; alternatively, disabled regions may be shown with a clear “No routes yet” state if product owners decide that is useful.
- Back returns to home or previous screen without unexpectedly losing a draft.

6.2 Screen: City selection
Header:
- Back button.
- Selected province/region.
- Title: “Choose a city”.
- Search field/button.
- Optional speaker control.
- Progress indicator.

City cards:
- City illustration or appropriate city/landmark graphic.
- City name in selected language.
- Optional subtitle such as “Services available”.
- Avoid unverified route-count badges.

Data rules:
- Display all configured cities in the selected region that have a Quetta route.
- Do not hardcode the destination list into the app; fetch it from backend-managed route data.
- A city may be visible because a route exists generally, but final availability depends on the selected travel date and service.
- If no cities are available, explain that there are no configured destinations in that region yet and provide Back.

Search behavior:
- Search matches English and Urdu names/aliases where supported.
- Keyboard can be dismissed with a clear button.
- Voice search is optional.
- If voice recognition fails, display a manual selection list.
- Selecting a city advances to vehicle type.

6.3 Screen: Choose Cars or Buses
Header:
- Back button.
- Destination summary (for example, “Quetta → [selected city]”).
- Title: “Choose your transport”.
- Progress indicator.

Two large cards:
A. Cars
- 3D-style car illustration.
- Label: Cars.
- Supporting text: “View available cars”.
- Entire card tappable.
- Tap sets vehicle category to Cars and continues to travel date/results.

B. Buses
- 3D-style bus illustration.
- Label: Buses.
- Supporting text: “View available buses”.
- Entire card tappable.
- Tap sets vehicle category to Buses and continues to travel date/results.

Card behavior:
- Clearly show selection state.
- Do not show vehicle type as available unless services exist or are configured.
- If no matching service is available on the selected date, show the no-results state rather than fabricated inventory.

6.4 Screen: Select travel date
The user requested the date be chosen before the final list of available journeys is displayed.

Elements:
- Large “Today”, “Tomorrow”, and calendar options where applicable.
- Calendar date picker.
- Selected date displayed in a clear format.
- Optional spoken date.
- Continue/Search button.

Behavior:
- Prevent selection of invalid past dates for new bookings.
- Display local date/time consistently.
- Date changes refresh results.
- Preserve selected province, city, and vehicle type.
- If a chosen date has no service, provide nearby dates as optional alternatives without changing the date silently.

6.5 Screen: Available journeys list
Title:
- “Available Cars to [City]” or “Available Buses to [City]”.
- Show selected date.
- Show route summary: Quetta → destination.
- Provide Back/Edit Search action.

Every result card should include, where known:
- Vehicle type and image/photo.
- Operator/service name, if applicable and approved for display.
- Scheduled departure time.
- Estimated arrival time.
- Estimated journey duration.
- Ticket fare per passenger/seat.
- Number of seats currently available.
- Boarding location.
- Relevant intermediate stops.
- Any relevant service conditions.
- Prominent “Select Seats” button.

Arrival-time display:
- Label as “Estimated arrival” unless the operator guarantees the time.
- If an estimate is unavailable, show “Arrival estimate unavailable” rather than inventing one.
- Duration must be derived from configured schedule/estimate, not fabricated.

Fare display:
- Show fare in PKR with clear formatting.
- State whether price is per seat/passenger.
- Include any mandatory fees transparently before final confirmation.
- Never use example/demo values as actual fares.
- If price is unknown or not validated, do not present a fake price; show an appropriate unavailable state and do not allow an invalid booking.

Availability:
- Use current server-validated inventory.
- A displayed seat count can become stale; revalidate when the passenger opens/selects seats.
- Do not promise a seat until a valid temporary hold/booking process succeeds.

Sort/filter suggestions:
- Sort by earliest departure, lowest fare, or arrival time if enough reliable data exists.
- Any sort/filter control must be clearly labeled and easy to reset.
- Keep the default result list simple; do not overwhelm first-time users.

No-results state:
- Clear message: “No journeys available for this date.”
- Buttons: “Choose another date” and “Change destination”.
- Optional nearby-date suggestions only if real schedules can be checked.
- Never invent availability to fill the screen.

Failure/offline state:
- State that current availability cannot be confirmed.
- Provide Retry.
- Do not allow an unverified offline result to appear bookable.

6.6 Selecting a result
Tap “Select Seats”:
- Revalidate service, fare, schedule, seat inventory, and booking eligibility with backend.
- Open the correct seat map for the specific vehicle.
- If the service has become unavailable, explain this and return to refreshed results.
- If a fare changes due to an authorized update before booking, show the new fare and require passenger acknowledgement before continuing.

7. SEAT MAP AND BOOKING CHECKOUT
======================================================================

7.1 Seat map
- Show vehicle type and route at top.
- Provide a simple legend with text and visual markers:
  Available, Selected, Unavailable/Booked, and any other supported state.
- Do not rely on color alone.
- Use a vehicle-specific seat layout.
- For a standard car, the current planning rule is five seats total: one driver seat, one front passenger seat, three rear passenger seats. The driver seat is never sold.
- Vans, Coasters, and buses require their own configured layout and capacity.
- Do not assume every vehicle has the same arrangement.

7.2 Seat selection
- Tap an available passenger seat to select it.
- Tap selected seat again to deselect it before confirmation.
- Show selected seat number(s) clearly.
- Show live price summary.
- If a seat is taken by another booking, mark it unavailable and explain simply.
- Seat holds are temporary and server-controlled. Existing planning specifies a 10-minute seat hold; countdown must reflect server state.
- Do not claim a seat is held until backend confirms the hold.
- When a hold expires, explain that the seat is no longer reserved and refresh availability.

7.3 Luggage feature removed
- Do not provide a luggage-selection screen, included-bag counter, luggage allowance picker, extra-bag option, or luggage fee.
- Do not implement the previous “one standard bag” rule or PKR 500 extra-luggage charge.
- The only passenger-facing luggage-weight rule in this app blueprint is the plain-language 10 kg limit per booked seat, explained in the Privacy Policy and Help section only.
- Do not display the 10 kg rule in checkout, booking review, payment, or fare summaries.

7.4 Passenger details
- Keep the form short and readable.
- Use saved verified details where allowed.
- Clearly label required fields.
- Avoid asking for the same data repeatedly.
- Protect CNIC and other sensitive data; do not expose it in public ticket QR payloads or notifications.
- Explain why any required identity information is needed.

7.5 Booking review
Show:
- Origin and destination.
- Travel date.
- Vehicle/service.
- Departure and estimated arrival.
- Boarding point.
- Selected seats.
- Passenger count.
- Ticket rate for the selected journey.
- Total ticket price only.
- Do not add separate highway fees, toll fees, luggage charges, or other fee line items to the checkout UI. The checkout amount is the ticket rate for the selected journey.
- Applicable cancellation/refund policy summary.
- Payment method and current payment/booking status.

Buttons:
- Back/Edit: return to relevant prior step without losing data unnecessarily.
- Confirm and Pay / Confirm Booking: label according to actual payment flow and provider availability.
- Help: open booking support.
- Do not show a successful booking screen until server confirmation.

7.6 Payment
- Payment methods are displayed only when actually configured and available.
- Do not promise payment-provider support before integration, cost, settlement, and refund handling are validated.
- Prevent duplicate booking/payment on repeated taps or slow networks.
- For uncertain payment status, show “Checking payment status” and reconcile with backend; do not immediately claim success or failure.
- Do not collect/store card or wallet secrets outside an approved secure provider flow.

7.7 Booking confirmation
After backend confirms:
- Show clear success icon and “Booking confirmed”.
- Show booking reference and ticket access button.
- Show QR ticket only if ticket is valid and confirmed.
- Show journey summary and boarding location.
- Offer “View Ticket”, “My Trips”, and “Home”.
- Optional share action must avoid exposing unnecessary personal information.
- Send notification only through configured channels and report delivery status accurately where known.

8. MY TRIPS — DETAILED BLUEPRINT
======================================================================

Screen title: My Trips.

Tabs:
1. Upcoming
2. Completed
3. Cancelled

Trip card content:
- Origin → destination.
- Travel date.
- Departure time.
- Vehicle type.
- Booking status.
- Boarding location.
- “View Trip” button.

View Trip screen:
- Full route and service details.
- Departure and estimated arrival.
- Boarding point and instructions.
- Ticket/QR shortcut.
- Applicable contact/support option.
- Journey updates where supported.
- Cancellation option only when permitted.
- Refund summary and current refund status.
- Safety/help action.

Cancellation behavior:
- Before final cancellation, show the applicable refund amount and retained amount.
- Existing planning rule: within the first 8 hours after booking confirmation, refund 100%; after the first 8 hours, refund 75% and retain 25%; exactly 8 hours receives the 75% refund rule as previously specified. The time calculation starts at booking confirmation, not departure.
- Driver cancellation: attempt a suitable replacement at company cost; if no suitable replacement is available, full refund.
- Passenger no-show caused by passenger-controlled reasons has no automatic refund; company-caused delays or incorrect information receive protection.
- These are existing planning requirements and must be reviewed for legal/commercial compliance before launch.
- Never tell the user a refund is completed until payment/backend status confirms it.

Empty states:
- Upcoming empty: “No upcoming trips” + Book a Journey.
- Completed empty: “No completed trips yet”.
- Cancelled empty: “No cancelled trips”.
- Loading/error states must be clear and retryable.

9. MY TICKETS — DETAILED BLUEPRINT
======================================================================

Purpose: fastest access to a confirmed ticket and QR code.

Ticket list:
- Separate upcoming/current and past tickets if useful.
- Clear confirmed/cancelled/pending state.
- Pending bookings must not appear as confirmed tickets.

Ticket detail:
- Vashسفر identity.
- Booking reference.
- Passenger name as appropriate.
- Origin and destination.
- Date and departure time.
- Estimated arrival.
- Vehicle/service.
- Seat number(s).
- Boarding point.
- QR code for server-validated ticket.
- Ticket status.

Buttons:
1. Show QR Code — opens a large, bright, high-contrast QR view.
2. View Full Ticket — opens complete details.
3. Share Ticket — uses Android sharing with privacy safeguards.
4. Get Directions — opens supported map/navigation for the boarding point, if available.
5. Contact Support — opens ticket-specific help.
6. Back — returns to ticket list.

QR rules:
- Do not put CNIC, full phone number, or other sensitive data directly into a readable QR payload.
- QR must be verifiable against backend rules.
- Invalid/cancelled/used ticket status must be checked.
- A screenshot of a QR is not proof of a currently valid ticket.
- Hide bottom navigation during full-screen scanning/QR presentation if it improves usability.
- If offline validation is supported for staff, duplicate-use and later reconciliation rules must be defined; do not promise perfect duplicate prevention without connectivity.

No-ticket state:
- Illustration of a ticket.
- Message: “You don't have a confirmed ticket yet.”
- Button: Book a Journey.

10. HELP AND SUPPORT — DETAILED BLUEPRINT
======================================================================

Help screen should be approachable, simple, and divided into four illustrated cards.

10.1 Booking Help
Topics:
- How to book a seat.
- How to choose a province and city.
- How to choose Cars or Buses.
- How to select a travel date.
- How to understand fares and arrival estimates.
- How to find My Trips and My Tickets.
- How to show a QR ticket.

10.2 Payment & Refunds
Topics:
- Payment pending/failed/unknown.
- How to check payment status.
- Cancellation policy.
- Refund status.
- Reporting an incorrect charge.
- Never ask a user to share a PIN, OTP, or password with support.

10.3 Journey Help
Topics:
- Finding boarding point.
- Departure delay.
- Missed departure.
- Seat luggage-weight limit: explain that luggage associated with a booked seat must not exceed 10 kg. Show this information in Help, not during checkout.
- Lost belongings.
- Contacting the service/operator where available.
- Route or vehicle changes.

10.4 Emergency Assistance
- Passenger SOS.
- Serious safety concern.
- Urgent journey assistance.
- Explain the action before or during activation where doing so does not delay a real emergency.
- Avoid accidental activation with a deliberate interaction pattern, but do not make genuine SOS unnecessarily difficult.
- Never guarantee that an SOS message/call was delivered if no communication channel is available.
- SOS should include only necessary trip/location information and respect permissions and privacy rules.

Support contact options:
- Call Support only when a verified working number is configured.
- Chat/WhatsApp only if officially configured, staffed, and consent/privacy requirements are met.
- Report a problem form with category, trip reference, description, and optional attachment if supported.
- Show complaint/reference number after backend confirms submission.
- Show expected response time only if an actual service target has been approved.

11. SETTINGS — DETAILED BLUEPRINT
======================================================================

Settings sections:

11.1 Language
- English.
- Urdu.
- Save selection.
- Apply correct RTL layout for Urdu.
- Remember selection between sessions.
- First-launch language choice is shown once; user can change it later.

11.2 Voice Assistance
- Enable/disable spoken instructions.
- Repeat last instruction.
- Spoken language.
- Voice search enable/disable.
- Explain microphone permission.
- Manual selection remains available at all times.

11.3 Notifications
- Booking confirmation/status.
- Departure reminders.
- Schedule/route changes.
- Refund status.
- Important safety announcements.

11.4 Account

- Verified phone status.
- Account support.
- Do not expose privileged account controls.

11.5 Security
- Supported sign-in/session options.
- Sign out of current device.
- Sign out of other devices if supported.
- Re-authenticate for sensitive account changes.
- Never display or ask users to share passwords/OTPs in plain support messages.

11.6 Accessibility
- Text-size control if supported.
- High-contrast option if supported.
- Reduce motion if supported.
- Voice assistance shortcut.
- Ensure settings do not break layout.

11.7 Payments
- Display available payment methods.
- Manage payment preferences only where provider integration supports it.
- Show relevant transaction history if included and authorized.
- Do not store provider secrets in the app.

11.8 Privacy
- Explain location use.

37. SCREEN-BY-SCREEN VISUAL BLUEPRINT — PASSENGER HOME SCREEN
======================================================================

PURPOSE
The passenger Home screen is the friendly starting point for finding a journey from Quetta to a configured destination. It must make the next action obvious even for a person who reads slowly or has limited experience using smartphone apps. It should feel calm, trustworthy, welcoming, and premium without becoming crowded.

SCOPE
- This section describes only the Vashسفر passenger-facing app.
- It does not define the Vashsafar Admin app or Silent Owner website.
- The default journey origin is Quetta, unless the route inventory and product rules later permit another origin.
- Only destinations with configured, bookable services should appear as available choices.
- Use the approved navy-blue direction as a working design decision. Color values remain subject to later visual review.

A. SCREEN CANVAS AND SAFE AREAS
1. Design reference viewport: 360 × 800 dp, portrait Android phone.
2. Also test compact 320 dp-wide phones, common 360–393 dp phones, and larger devices.
3. Respect Android status-bar and navigation/system gesture insets. Do not place essential text or buttons beneath system UI.
4. Use a vertically scrolling content area. The bottom navigation remains anchored above the system navigation area and does not scroll with the content.
5. Keep the primary content within approximately 16 dp horizontal margins. Use 12–16 dp between major cards and 8 dp between related controls.
6. Do not force the whole Home screen to fit without scrolling on a small device. The primary journey-search action and bottom navigation must remain easy to reach.

B. VISUAL HIERARCHY FROM TOP TO BOTTOM

ZONE 1 — HEADER
Approximate height: 64–76 dp, excluding the system status bar.
- Background: deep navy (#071A2D) or the approved primary navy (#102A43); keep one consistent header treatment throughout the app.
- Left: Vashسفر wordmark. Use the approved brand treatment only; do not imitate Easypaisa branding.
- Center/near the wordmark: a short greeting such as “Where would you like to go?” with an Urdu equivalent when Urdu is selected. Avoid a long welcome paragraph.
- Right: a circular Help/support shortcut or notification shortcut only if the product team confirms which one is most important. Do not crowd the header with multiple small icons.
- If both notifications and Help are needed, keep Help in the bottom navigation and use the header icon for notifications.
- Touch target for any icon: at least 48 × 48 dp, even if the visible icon is smaller.
- Header should not contain account balances, advertising banners, or unrelated promotional clutter.

ZONE 2 — ORIGIN AND DESTINATION SUMMARY
Approximate card height: 88–104 dp.
- Place a prominent white or very light neutral card below the header, with 16 dp internal padding and 16 dp corner radius.
- First row: small label “From” / Urdu equivalent, then “Quetta” in larger, high-contrast text.
- Second row: label “To” / Urdu equivalent, followed by a clear prompt such as “Choose destination”.
- Use a simple route line or arrow illustration between origin and destination. Keep the graphic decorative and understandable; do not let it compete with the destination label.
- If the product rules allow origin changes in a future release, origin editing must be explicit and controlled. For the current flow, show Quetta as the origin and do not imply all cities can be used as origins.
- Tapping the destination area opens the Region/Province selection screen.
- If a destination has already been selected in the current search draft, display that city rather than the prompt.
- The entire destination row should be tappable, not only the tiny arrow icon.

ZONE 3 — PRIMARY JOURNEY SEARCH CARD
Approximate height: 160–190 dp depending on localization and device width.
- Use a high-contrast white card with rounded corners (16 dp) and a subtle elevation or border. Avoid heavy shadows.
- Card title: “Find a journey” / Urdu equivalent, in a clear 20–22 sp semibold style.
- Include a compact visual sequence: Region/Province → City → Vehicle type. This is a visual explanation, not a second set of competing controls.
- Show the current selection state in simple text, for example “Choose a destination to begin”.
- Main action button: full-width navy-blue button, minimum 52 dp high, 12 dp corner radius, white bold label such as “Choose destination”.
- If the destination is already selected, change the button label to “Choose car or bus” or the next valid step. Do not let the button silently skip a required step.
- The main button must have a visible pressed state and a loading state when a request is actually in progress.
- Tapping it opens the next missing step in the flow: Region/Province, then City, then Cars or Buses, then journey results. Do not ask the user to repeat information already selected and still valid.

ZONE 4 — VEHICLE CATEGORY ILLUSTRATIONS
Approximate top-to-bottom area: 180–240 dp; may be partly below the fold on compact phones.
- Display two large illustrated cards: “Cars” and “Buses”.
- Each card should use a clear, friendly, original illustration or 3D-style icon, with the label directly beneath or alongside it. Use the same illustration style and visual weight for both categories.
- On 360 dp width, use a two-column layout if each card retains a comfortable tap target and readable label. On narrow screens, stack the cards vertically or use a compact two-column layout with sufficient width; do not shrink the artwork and labels until they become hard to recognize.
- Suggested card treatment: light background, 16 dp rounded corners, 12–16 dp padding, 112–136 dp approximate height.
- Keep illustrations culturally neutral and recognizable. Avoid tiny details, text embedded inside the image, or color-only distinctions.
- Tapping Cars opens the vehicle-category step for the selected destination if one exists; otherwise ask the user to choose a destination first.
- Tapping Buses behaves the same way.
- If a category has no configured journeys for the selected route/date, do not show a false availability claim. Either hide it or show it disabled with a plain explanation, depending on the unresolved product decision in Section 36.
- Do not show prices on these Home category cards unless product owners later decide that a verified, route-specific “from” price is useful. A generic price can mislead users.

ZONE 5 — UPCOMING OR RECENT TRIP CARD (CONDITIONAL)
- Show this zone only when the passenger has a relevant upcoming confirmed trip or a useful recent-trip action.
- If there is an upcoming confirmed trip, show a concise card with destination, date, departure time, and a “View ticket” action.
- Do not show private ticket details on a logged-out Home screen or expose a QR code on the Home screen.
- If there is no upcoming trip, do not fill the area with an empty placeholder. Prefer no card or a small, non-intrusive recent-search section if supported.
- A pending payment or pending offline ticket must be labelled accurately; never present it as confirmed.

ZONE 6 — TRUST AND HELP SHORTCUT
- Use one compact reassurance row near the lower part of the scrollable content, such as “Need help booking?” with a Help action.
- Avoid unsupported claims such as “100% safe” or “guaranteed arrival”.
- If SOS is available, keep it in the appropriate trip context and/or Help area; do not make a large red SOS button part of ordinary journey discovery. Emergency access must still be quick when a journey is active.

ZONE 7 — FIXED BOTTOM NAVIGATION
Height: approximately 64–72 dp plus system inset as required.
Five items in this order:
1. Home
2. My Trips
3. My Tickets
4. Help
5. Settings

- Use an icon plus a short text label for every item. Icons alone are not sufficient for this low-literacy design.
- The active item uses a clear navy accent and/or a softly tinted background; inactive items retain strong enough contrast.
- Keep all five touch targets evenly distributed and at least 48 dp high.
- Use simple, consistent icons. Do not use different icon styles in the same bar.
- Do not place a sixth item in the bottom navigation.
- Urdu mode must support right-to-left layout and natural label order while preserving the intended meaning and accessibility labels.
- Tapping a navigation item opens that section and preserves safe in-progress search choices where practical.

C. TEXT, COLOR, TYPE, AND COMPONENT RULES
- Primary navy: working token #102A43.
- Deep navy: working token #071A2D.
- Secondary blue: working token #1F4E79.
- Use a light neutral page background and white cards for contrast.
- Use near-black/navy text for body copy on light surfaces and white text on dark surfaces.

- Prefer short everyday words. Avoid English-only abbreviations and technical terms on passenger-facing screens.
- Use illustrations as supporting cues, never as the only explanation of an action.
- All interactive controls need a visible focus/pressed state and accessible label.

E. LOADING, EMPTY, ERROR, AND OFFLINE STATES

- Use a short skeleton or restrained loading indicator for dynamic destinations and upcoming trips.

- Secondary action: “Get help”.

- Do not imply the whole network has permanent service to every Pakistani city.

No upcoming trips
- Do not show an alarming error.

No internet connection
- If previously loaded destination data is available, it may be displayed with a clear offline indication, but availability and fares must be refreshed before a booking is confirmed.
- Disable actions that require a live server response, or let the user proceed only to clearly marked draft steps.
- Never claim a seat is reserved or a payment succeeded while confirmation is unknown.

Session expired
- Preserve non-sensitive search choices where safe.
- Ask the user to sign in again only when a protected action requires it.
- Do not expose another passenger’s trip or ticket data.

- Provide correct Urdu RTL layout, alignment, reading order, and mirrored directional graphics where semantically appropriate.

- Seat availability must be validated for the relevant route segment, not only for the vehicle as a whole.
- A card is not a reservation. Inventory must be checked again before a seat hold/booking is created.
- If the system uses a 10-minute seat hold, start that hold only when the booking flow successfully creates the hold; browsing results must not reserve a seat.
- A journey result can become unavailable between display and selection. Explain this gracefully and refresh the list.
- Do not promise a replacement vehicle, refund, or other outcome on the card unless the applicable policy supports it.

D. INTERACTION RULES

Action: Tap “Select journey”
1. Revalidate journey status, fare, route, date, and relevant seat inventory with the server.
2. If still valid, proceed to the approved next booking step (such as seat selection or passenger details, according to the vehicle/category workflow).
3. If the fare changed, clearly show the updated fare and require the passenger to acknowledge it before proceeding.
4. If the journey is no longer available, explain that it has changed or sold out, refresh results, and offer alternatives.
5. Do not charge the passenger simply because they tapped Select journey.

Action: Change route/date/category
- Open the relevant prior step with current selections prefilled.
- Re-run the search after the change.
- Do not keep incompatible results visible as if they still match.

Action: Sort results
- Sort only the currently returned valid results.
- Keep the selected search criteria unchanged.
- Make the active sort choice visible.

Action: Open boarding-point details
- Show the configured pickup/boarding information in a readable detail sheet or screen.
- Do not expose a driver’s private phone number or live location unless the approved product rules permit it at the appropriate stage.

Action: Refresh results
- Request updated results and availability.
- Keep the user’s search criteria.
- Show a restrained loading state rather than blanking the entire screen.

E. STATES

Loading
- Keep the app bar and search summary visible.
- Show journey-card skeletons or a concise progress indicator.
- Do not show invented placeholder prices or times.

Journeys available
- Show cards ordered by the approved default, which should be explicitly defined before implementation (recommended default: earliest departure).
- If sorting is offered, make the active order clear.

No journeys for this date/category
- Heading: “No journeys available for this selection.”
- Explain that there may be no configured departure for the selected date/category.
- Actions may include “Change date”, “Choose another vehicle”, and “Change destination”, as applicable.
- Do not suggest that the entire city is permanently unsupported if only that date has no departures.

No configured route
- Message: “This destination is not currently available from Quetta.”
- Offer Change destination and Help.
- Only use this message if route configuration confirms no service; do not use it for a temporary lack of departures.

Journey sold out or changed
- Message: “This journey is no longer available. We’ve refreshed the results.”
- Remove or update the stale card.
- Offer other available journeys without silently substituting a different journey.

Network/server error
- Message: “We couldn’t refresh journeys.”
- Actions: Try again and Get help.
- Cached results, if shown, must be clearly marked as not current and must not be bookable without revalidation.

Fare changed
- Show the previously displayed fare only if useful and accurate, alongside the new fare.
- Explain that the fare changed.
- Require acknowledgement before continuing; never silently charge the new amount.

No valid arrival estimate
- Do not show a fabricated arrival time.
- Use an approved unavailable label or omit the estimate while preserving the departure and route details.

PART 1 — UNIVERSAL INTERACTION CONTRACT
======================================================================

1.1 Every interactive element needs a written contract
For every button, link, card, icon, field, switch, tab, row, map marker, seat, QR action, and system-permission prompt, the implementation specification must define:
- Unique UI element ID / analytics event name.
- Screen where it appears.
- Visible label in English and Urdu.
- Enabled, disabled, loading, success, and failure states.
- What a tap does.
- Whether it navigates, opens a sheet/dialog, changes local state, or calls the backend.
- The exact backend operation or read query, if any.
- Input validation before a request.
- Duplicate-tap behavior.
- Loading indicator and timeout behavior.
- Success message and destination.
- Error message and recovery button.
- Back-navigation behavior.
- Accessibility label, focus order, and touch target.
- Whether the action is safe to retry.
- Security / authorization check required on the server.
- Tests proving the behavior.

1.2 Standard touch and loading behavior
- Make primary actions at least 48 dp high/wide; aim for larger targets on the main home cards.
- A tap must visibly register immediately, even if a network request is still running.
- Disable a submit button while its request is in progress, but do not make the whole screen appear frozen.
- Use a spinner plus a short status label for actions that may take more than a brief moment.
- Prevent duplicate purchases with both client-side button locking and server-side idempotency.
- Never depend on client-side locking alone to prevent duplicate bookings or payments.
- If a user taps a disabled control, show a short reason where practical.
- Keep keyboard focus and screen-reader focus predictable after dialogs, errors, and navigation.
- Use a confirmation dialog for destructive or financially consequential actions, but do not add unnecessary confirmation steps to harmless navigation.
- A dialog must have an explicit safe exit unless the user is in a critical flow that cannot safely be dismissed.
- The Android system Back action must match the visible Back button wherever possible.

1.3 Standard button verbs
Use consistent verbs:
- Continue: validate current step, then move forward.
- Back: return to the prior step without losing safe local choices.
- Search: validate fields and retrieve matching results.
- Retry: repeat a safe read or idempotent operation.
- Confirm booking: final booking commitment, only after showing the applicable fare and policy.
- Pay now: hand off to the approved payment process.
- Cancel booking: open a summary of consequences, then require explicit confirmation.
- Contact support: open the configured support channel only if it is actually available.
- Try again: retry an operation after a recoverable error.
- Go to Home: navigate to Home and clearly warn if unsaved changes would be lost.
- Save changes: validate and persist the exact settings shown.
Do not use vague button labels such as “OK” where a more meaningful label is possible. “OK” may be used only to dismiss a simple informational message.

1.4 Network request policy
- All booking-critical decisions must be server-authoritative: journey inventory, seat availability, seat holds, fare, booking status, payment status, cancellation eligibility, refund status, QR validation, and boarding status.
- The app may show cached data as cached, but cached data is not proof that a seat remains available.
- Read requests may use bounded retry with exponential backoff and jitter.
- Do not automatically retry a non-idempotent payment or booking creation unless the backend supports an idempotency key and can return the existing result.
- On timeout, use neutral wording: the result is unknown until status is checked. Never tell the user that a transaction failed if the server may have completed it.
- Use request IDs / correlation IDs for troubleshooting. Do not show internal stack traces, database messages, keys, or raw provider responses to users.
- Log technical detail securely on the server, with sensitive fields redacted.
- Do not retry forever. After a small number of safe retries, show a clear manual Retry action.
- Respect Android connectivity changes and app lifecycle; when the app returns from background, re-check time-sensitive booking state.

1.5 Message design
Every error message should tell the user:
1. What happened, in plain language.
2. Whether their booking/payment/selection is safe or still pending.
3. What they can do next.
4. Which button to tap.
Avoid blame, unexplained codes, and technical jargon.
Provide equivalent English and Urdu translations. The English examples below are canonical draft copy; Urdu copy must be reviewed by a fluent Urdu writer before release.
Never put personal data, full payment credentials, internal IDs, SQL errors, stack traces, secret values, or security-sensitive details into a user-visible message.

5.1 Seat selection screen

- Booked/unavailable: not selectable.

- A tap on an unavailable seat does not silently select it; show “This seat is unavailable. Choose another seat.”

- Never allow a seat to be sold twice for overlapping route segments.
- Segment-based seat reuse is permitted only when the route/segment inventory model proves that occupied segments do not overlap.
- The backend, not the client, decides whether a seat is available.
- Hold expiration must be checked server-side, not only by the phone timer.

Seat-selection errors:
- Seat map not configured: “Seat selection isn’t available for this vehicle. Please choose another journey or contact support.”
  Buttons: “Back to journeys” -> results; “Help” -> support.
- Seat inventory loading: “Checking available seats…”
  Do not allow selection until state is known.
- Seat became unavailable: “That seat was just taken. We’ve refreshed the seats; choose another one.”
  Button: “Choose another seat” -> current seat screen.
- Hold request timed out: “We couldn’t confirm your seat hold. Check availability before continuing.”
  Buttons: “Check seats” -> query server; “Back” -> results.
- Hold rejected: “We couldn’t hold those seats. They may no longer be available.”
  Buttons: “Refresh seats” -> refetch; “Choose another seat” -> seat view.
- Hold expired: “Your 10-minute seat hold has expired. Choose available seats again.”
  Buttons: “Choose seats” -> refresh seat map/list; “Back to journeys” -> results.
- Network lost during hold: “Your seat hold hasn’t been confirmed. Reconnect and check availability.”
  Button: “Check availability” -> server status check, not blind re-hold.
- Server conflict / overlapping segment: “This seat is not available for the full selected journey. Choose another seat.”
  Button: “Choose another seat” -> current seat view.

5.2 Hold lifecycle
- The server creates a hold with a unique hold ID, user ID, journey/segment identifiers, seat IDs, created timestamp, expiry timestamp, and state.
- Expiry is calculated using server time.
- Hold creation is atomic: either all requested seats are held or none are, unless the product explicitly supports partial selection and clearly tells the user.
- The client countdown is only a display estimate.
- Re-check hold status before booking review and before final booking creation.
- On expiry, release the hold server-side via expiry processing and treat expired holds as invalid in all booking queries even if cleanup is delayed.
- Do not rely solely on a scheduled job to make expired seats available; availability queries must ignore expired holds.
- On app resume, refresh hold status and remaining time.
- When the user leaves the booking flow, release the hold where appropriate; if release fails, server expiry remains the safety mechanism.
- Never allow a client to extend its own hold arbitrarily.

6.1 Payment method screen

  Button: “Help” -> support.

  Buttons: “Choose another method” -> method list; “Try again” -> recheck provider status.
- Payment method not supported: “This payment method can’t be used for this booking.”
  Button: “Choose another method” -> list.
- Booking/hold expired before payment: “Your seat hold expired before payment could start. Check seats again.”
  Button: “Check seats” -> seat selection.

6.2 Starting a payment
- Create a booking/payment intent on the server with a unique idempotency key.
- Server revalidates the seat hold, fare, and booking state before requesting payment.
- Use a provider-hosted secure payment flow or a vetted SDK; do not collect raw card credentials in ordinary app fields.
- Never store card PINs, OTPs, full card numbers, or payment secrets in the app database or logs.
- Record provider reference IDs and minimal status needed for reconciliation.
- If the provider returns a redirect/deep link, validate the callback and do not trust a client-supplied “success” flag.
- A provider callback/webhook must be verified server-side using the provider’s documented signature/authentication method.
- Do not mark a ticket confirmed solely because the app returns from a payment screen.

6.3 Payment states
- CREATED: server created payment attempt.
- REQUIRES_ACTION: user must complete provider flow.
- PROCESSING: waiting for provider result.
- SUCCEEDED: provider result verified; booking can be confirmed if all booking checks pass.
- FAILED: provider has definitively failed the attempt.
- CANCELLED: provider confirms cancellation or the payment intent is safely cancelled.
- UNKNOWN / RECONCILIATION_REQUIRED: outcome uncertain; query provider/server before offering another charge.
These are conceptual states; exact provider mapping must be documented during implementation.

6.4 Payment messages and buttons
User cancelled payment and provider confirms cancellation:
Message: “Payment was cancelled. Your booking is not confirmed.”
Buttons: “Try payment again” -> create/resume safe attempt if hold remains valid; “Return to booking” -> review/seat flow.

Payment declined:
Message: “The payment didn’t go through. No ticket has been confirmed.”
Buttons: “Try another method” -> payment methods; “Try again” -> retry only if provider confirms safe failure; “Help” -> support.

Payment pending:
Message: “Your payment is still processing. Please don’t pay again yet.”
Buttons: “Check payment status” -> backend status query; “My Tickets” -> ticket list showing pending status; “Help” -> payment support.
Do not show a second Pay now button until the prior attempt has been reconciled.

Payment result unknown / network drops after Pay now:
Message: “We couldn’t confirm the payment result. Please check its status before trying to pay again.”
Buttons: “Check payment status” -> query backend/provider; “Help” -> support.
Never say “payment failed” until failure is definitive.
Never initiate another charge on a blind retry.

Payment succeeded but booking confirmation is delayed:
Message: “Your payment appears successful, but your ticket is still being confirmed. Please wait or check status. Don’t pay again.”
Buttons: “Check booking status” -> backend reconciliation; “My Tickets” -> pending ticket state; “Contact support” -> support.
Backend must reconcile provider success with booking/seat inventory and invoke the approved recovery policy if the booking cannot be completed.

Payment screen closes unexpectedly:
On return to app, query the server using the existing booking/payment attempt ID. Do not create a new attempt automatically.

6.5 Ticket confirmation
Show success only after the backend confirms booking and payment status.
Success copy: “Booking confirmed. Your ticket is ready.”
Buttons:
- “View ticket” -> ticket detail.
- “My Tickets” -> ticket list.
- “Back to Home” -> Home.
- “Share trip details” (optional) -> share only non-sensitive trip summary; never share a private QR ticket by default.
If QR generation fails, do not invalidate the booking; show the confirmed ticket details and a “Refresh ticket” action.
If the ticket record is delayed, show pending status and status-check action, not a fake success screen.

- A second scan shows: “This ticket has already been scanned. Check its current status before boarding.”
- Invalid QR shows: “We couldn’t verify this ticket. Check the ticket details or contact the trip supervisor.”
- Offline scan must be explicitly marked unverified and follow a defined operational fallback; do not claim perfect duplicate prevention while offline.
- Passenger UI may show their QR, but must not expose staff-only manifest or scanning controls.

8.2 Refund state

- NOT_APPLICABLE
- ELIGIBILITY_CHECK
- REQUESTED
- APPROVED
- PROCESSING
- SUCCEEDED
- FAILED
- NEEDS_REVIEW
Store the policy version, cancellation timestamp, booking-confirmation timestamp, fare basis, refund percentage, amount, currency, provider reference, and audit event.
The server computes refund eligibility and amount. The app displays the server result.
Do not let the Android client decide its own refund amount.

8.3 Operator cancellation / trip disruption

- If no replacement is available, show the approved full-refund path.
- Provide Help/contact support.
- Preserve access to the ticket and status history.
- Never hide a cancellation notification because the passenger is offline; show it on next successful sync.

PART 11 — SUPABASE / POSTGRESQL BACKEND OPERATING DESIGN
======================================================================

IMPORTANT:
- Supabase is a candidate backend in this plan, not a claim that a project already exists.
- Confirm current Supabase product behavior, limits, pricing, region availability, and security guidance before implementation.
- Use official Supabase documentation during implementation and keep a record of the versions/features chosen.
- The following is a recommended architecture, not a substitute for an experienced backend/security review.

11.1 Recommended service boundaries
Android client:
- UI, accessibility, local navigation, safe cache, input validation, display.
- Calls approved backend APIs using the user's authenticated session.
- Must not decide authoritative fare, seat inventory, payment success, refund amount, or role permissions.

Supabase Auth:
- Identity/session management.
- Phone OTP only if configured with a supported SMS provider and acceptable cost.
- Enforce provider rate limits and application-level abuse protection.
- Use short, appropriate session lifetimes and secure token storage according to platform best practice.

PostgreSQL:
- Authoritative structured data.
- Foreign keys, check constraints, uniqueness rules, indexes, transactions, and row-level security.
- Enforce inventory and booking invariants at the database/server layer.

Supabase Edge Functions or a trusted backend service:
- Server-side operations requiring secrets, provider API calls, complex validation, and controlled transactions.
- Examples: create seat hold, confirm booking, create payment intent, verify payment webhook, cancel booking, compute refund, generate/validate QR, process SOS escalation, and perform privileged role operations.
- Keep functions small, auditable, versioned, and idempotent where appropriate.
- If a workload needs long-running jobs or features not suited to an edge function, use an appropriately secured server/worker instead of forcing all work into one function.

Supabase Realtime:
- Optional for refreshing seat availability, trip status, or operational updates.
- Realtime is a notification mechanism, not the final authority for booking. Re-check authoritative data before holding/booking.
- Do not broadcast private passenger information to broad channels.

Supabase Storage:
- Use only for files actually required, such as approved public assets or private support attachments.
- Keep private documents in private buckets with restrictive access policies and short-lived signed URLs where appropriate.
- Never put service-role keys, payment secrets, master recovery keys, or raw authentication credentials in storage accessible to the client.

Scheduled jobs / background workers:
- Expire/clean old seat holds, process reminders, reconcile uncertain payments, update derived operational status, and run retention/deletion workflows.
- Correctness must not depend solely on a scheduled cleanup: every query and transaction must treat an expired hold as expired using server time.
- Scheduled jobs must be authenticated, observable, idempotent, and safe to retry.

11.2 Secrets and environment separation
- Maintain separate development, staging/test, and production projects/environments.
- Never use real passenger/payment data in development test environments unless explicitly authorized and protected.
- Client app may contain only public project configuration and the publishable/anon key intended for client use, with correct Row Level Security.
- Never embed the Supabase service-role key, database password, payment provider secret, webhook secret, SMS provider secret, master key, or recovery key in Android source, APK, website JavaScript, logs, analytics, screenshots, or repository history.
- Keep server secrets in approved server-side secret storage.
- Rotate any secret that may have been exposed; do not rely on deleting it from source control.
- Restrict production access by least privilege and use MFA for privileged developer/owner accounts where supported.
- Do not print secret values in build logs or error reports.

11.3 Row Level Security (RLS)
- Enable RLS on every exposed table that contains user or business data.
- Write explicit policies for SELECT, INSERT, UPDATE, and DELETE as applicable; do not assume one policy safely covers all operations.
- Default-deny access where no explicit policy grants it.
- A passenger can read only their own profile, bookings, tickets, payment/refund status, and permitted support conversations.
- A passenger cannot directly set their own role, booking status, payment status, refund amount, seat hold owner, fare, boarding status, or operational permissions.
- A driver can read only the trips/manifests needed for their assigned work and only the passenger information necessary for that duty.
- A driver cannot read all users, all bookings, payment credentials, private owner records, or Silent Owner data.
- Operational workers/managers/owners belong to a separate authorization design for the separate Admin product; their privileges must not be inferred from a client-supplied role string.
- Public/anonymous users may read only intentionally public route/catalog data, and only fields intended to be public.
- Never expose internal notes, fraud signals, private audit records, or security events to ordinary passenger queries.
- Test RLS with positive and negative cases for every role.
- Do not use the service-role key to make ordinary client requests. It bypasses RLS and belongs only in tightly controlled server environments.

11.4 Authorization model
- Authentication answers “who is signed in?”
- Authorization answers “what is this identity allowed to do?”
- The server must check both for every privileged action.
- Do not trust role names, owner flags, user IDs, fares, seat status, refund amounts, or permissions sent in a request body.
- Privileged operations should check authorization on the server and record a private audit event.
- For the separate Admin system, preserve the specified distinction among workers, permission-based managers, three operational owners, and the single Silent Owner.
- Do not put Silent Owner authority into ordinary Supabase client metadata that a user could modify.
- The Silent Owner website must use a separate, strongly authenticated server-side control path; exact implementation requires a security review.

11.5 Database schema — proposed logical tables
Names are illustrative and must be reviewed before migrations are written.

A. profiles
- id (same identity UUID as Auth user, primary key / foreign key).
- display_name.
- contact details required for service.
- preferred_language.
- notification preferences.
- created_at, updated_at.
- Do not duplicate authentication secrets in this table.

B. regions
- id.
- name_en, name_ur.
- region_type (province, territory, or other configured classification).
- active flag.
- sort order.
- public display fields only.

C. cities
- id.
- region_id foreign key.
- name_en, name_ur.
- active flag.
- public display fields only.

D. routes
- id.
- origin_city_id (initial configured origin is Quetta).
- destination_city_id.
- route geometry/reference only if actually needed.
- active flag and operational status.
- created/updated timestamps.

E. boarding_points
- id, city/route relationship.
- public name/address.
- coordinates only if configured and appropriate.
- active flag.
- access notes.
- Do not fabricate boarding addresses or coordinates.

F. vehicles
- id.
- vehicle category.
- configured seat layout reference.
- operational status.
- vehicle identifiers only where needed.
- Keep driver and private operational details out of public queries.

G. vehicle_seats / seat_layouts
- layout ID, seat ID/label, seat position, selectable flag, seat type.
- Driver seat marked non-sellable.
- Layout must match the actual vehicle configuration.
- Do not assume every car, van, Coaster, or bus has the same layout.

H. journeys / scheduled_departures
- id.
- route_id, vehicle_id, assigned driver reference if operationally needed.
- departure timestamp with explicit timezone handling.
- estimated arrival data and whether it is estimated.
- status, configured fare, currency, booking cutoff, and operational metadata.
- Public response exposes only fields appropriate for passengers.

I. journey_segments
- journey ID and ordered segment definitions.
- Used only if segment-based booking and seat reuse are supported.
- Ensure segment ordering and boundaries are valid.
- Seat reuse is allowed only for non-overlapping segments and must be enforced transactionally.

J. seat_holds
- id.
- user_id.
- journey/segment reference.
- seat IDs or normalized hold-seat rows.
- created_at, expires_at, status.
- idempotency key / request identifier where appropriate.
- Hold expiry evaluated with server time.
- A unique/locking strategy must prevent overlapping active holds for the same seat and segment.

K. bookings
- id.
- passenger/user ID.
- journey ID.
- booking status.
- confirmed fare snapshot and currency.
- policy version.
- created/confirmed/cancelled timestamps.
- unique client request/idempotency key where applicable.
- Store fare snapshot so later fare changes do not rewrite a confirmed booking.

L. booking_seats
- booking ID.
- seat ID.
- journey segment references as needed.
- unique constraints to prevent overlapping confirmed allocation.
- Preserve an audit trail for changes; do not silently overwrite a seat assignment.

M. passengers / booking_passengers (only if multiple passengers are supported)
- booking ID.
- minimum required passenger details.
- Avoid collecting unnecessary sensitive data.
- Access restricted to the booking owner and authorized staff with a valid operational need.

N. payment_attempts
- id.
- booking ID or pending booking intent.
- provider name.
- provider transaction/reference ID.
- amount/currency snapshot.
- status.
- idempotency key.
- created/updated timestamps.
- Do not store raw card details, PINs, OTPs, or provider secrets.

O. payment_webhook_events / provider_events
- provider event ID with uniqueness protection.
- verified event type, safe payload subset, received timestamp, processing status.
- Store only the minimum provider data needed for reconciliation.
- Verify webhook authenticity before applying status changes.
- Duplicate webhook events must be idempotent.

P. cancellations / refunds
- booking ID.
- policy version.
- cancellation request timestamp.
- eligibility result.
- refund percentage and amount calculated server-side.
- provider refund reference.
- state and timestamps.
- audit event linkage.

Q. tickets
- booking ID.
- non-guessable ticket reference.
- QR token reference or signed-token metadata, not unnecessary personal details.
- status and issued/rotated timestamps.
- Do not expose predictable sequential IDs as the only ticket secret.

R. boarding_events
- ticket/booking ID.
- journey and authorized scanner/worker reference.
- timestamp.
- status and deduplication key.
- server-side uniqueness/atomic transition to prevent duplicate boarding.

S. trip_location_events / SOS events
- minimal GPS/safety data needed for the defined purpose.
- access tightly restricted.
- retention policy and automated deletion/review.
- separate SOS and breakdown events from routine trip history if required by policy.

T. support_cases / support_messages
- user/case reference, status, category, timestamps.
- private access to case owner and authorized support staff.
- redact secrets and unnecessary sensitive data.

U. notification_outbox / delivery_status
- event type, recipient reference, safe message template key, delivery status, retry count.
- Avoid storing excessive personal content.
- Use an outbox pattern so important notifications are not lost between a database change and message delivery.

V. audit_events
- append-only event record for sensitive business/security actions.
- actor, action, target type/reference, timestamp, result, correlation ID, and redacted metadata.
- Do not store access tokens, passwords, OTPs, full payment details, or master secrets.
- Limit who can read the audit trail; ordinary passengers cannot access it.

W. system_config / public_config
- Separate public configuration from private server secrets.
- Public app settings may include enabled regions/categories and feature flags safe for clients.
- Private keys, credentials, owner security controls, and provider secrets must not be exposed through this table or client-readable views.

11.6 Constraints and indexes
- Use foreign keys to prevent orphaned bookings, tickets, payments, and journeys.
- Use check constraints for valid status values and nonnegative fare amounts.
- Use unique constraints for provider event IDs, idempotency keys in their defined scope, ticket references, and other unique business identifiers.
- Index common lookups: active journeys by route/date/category, bookings by user/status/date, seat holds by journey/expiry, payment attempts by booking/provider reference, tickets by authorized booking/reference, and support cases by owner/status.
- Avoid over-indexing; validate query plans with realistic data.
- Use UTC timestamps internally with an explicit service timezone for user display; preserve original policy-relevant timestamps.
- Use numeric/decimal types appropriate for currency, not floating-point arithmetic.
- Currency is explicitly stored (for example, PKR) and never inferred from display locale alone.
- Migrations must be version-controlled, reviewed, repeatable in staging, and reversible where safely possible.
- Never manually patch production schema without a tracked migration and rollback/recovery plan.

11.7 Transactional seat allocation
- A seat is not reserved because it appears available on the screen.
- The server transaction must check the journey, seat layout, booking cutoff, segment boundaries, current confirmed allocations, and unexpired holds.
- Use database locking/transaction isolation/constraints appropriate to the chosen schema to prevent races.
- For a multi-seat request, hold all requested seats atomically or return a clear conflict.
- For segment-based reuse, compare every segment occupied by the proposed booking against all confirmed bookings and active holds for that seat.
- Do not rely on a client-side “isAvailable” boolean.
- If two passengers request the same seat at nearly the same time, exactly one valid hold/booking may win for overlapping segments; the other receives a conflict response and refreshed availability.
- The database design and concurrency behavior must be stress-tested before launch.

11.8 Booking transaction sequence
Recommended conceptual flow:
1. Client submits selected journey, seat IDs, passenger details, accepted policy version, and idempotency key.
2. Server authenticates user.
3. Server validates route/journey is active and bookable.
4. Server checks current fare and policy version.
5. Server validates the user's seat hold and expiry using server time.
6. Server verifies seat/segment availability transactionally.
7. Server creates or returns the existing booking intent for the idempotency key.
8. Server creates payment attempt if online payment is required.
9. Provider result is verified by server/webhook or trusted status lookup.
10. Server atomically updates payment and booking status when conditions are satisfied.
11. Server issues the ticket and safe QR representation.
12. Server writes an audit event and notification-outbox event.
13. Client fetches the authoritative result and shows confirmed/pending/failed state.

If any stage is uncertain, persist a recoverable state and reconcile; do not guess.

11.9 Fare rules
- Journey fare is configured on the server.
- Client may display a cached fare only as provisional until server validation.
- At final review/booking creation, server returns the current fare.
- Checkout displays the ticket rate as the payable amount under the current product decision.
- No separate highway fee or toll fee.
- No luggage fee, included-bag count, or extra-luggage purchase feature.
- Fare snapshots are attached to confirmed bookings.
- Fare changes require explicit user acknowledgement before proceeding.
- Fare updates require authorized business action and an audit record.
- The client cannot set its own fare or currency.

11.10 Supabase Auth and identity linkage
- Use the Auth user ID as the stable identity key for profile ownership.
- Do not use phone number alone as the permanent database primary key.
- Validate the JWT/session server-side for protected operations.
- Handle refresh-token rotation and sign-out securely according to current provider guidance.
- Apply rate limits to OTP, sign-in, and account recovery.
- Do not trust client metadata for privilege escalation.
- If custom claims are used, define how they are granted, updated, revoked, and refreshed; still enforce privileged operations server-side.

11.11 Edge Function / backend endpoints — proposed contract
These names are illustrative; the final API can differ. Every privileged function needs authentication, authorization, input schema validation, rate limits where appropriate, structured redacted logs, and tests.

Public/read operations:
- list_public_regions
- list_cities_for_region
- list_vehicle_categories
- search_journeys
- get_public_journey_details
- get_public_boarding_point
These return only safe public fields and must not reveal private operational data.

Authenticated passenger operations:
- get_my_profile
- update_my_profile
- get_my_trips
- get_my_tickets
- get_my_ticket_detail
- create_seat_hold
- get_seat_availability
- release_seat_hold
- create_booking_intent
- get_booking_status
- create_payment_attempt
- get_payment_status
- request_booking_cancellation
- get_refund_status
- create_support_case
- get_my_notification_preferences
- update_my_notification_preferences
- request_sos
Each operation must verify the signed-in user owns the referenced booking/hold/ticket/case or has the proper authorization.

Trusted provider callbacks / internal operations:
- payment_webhook
- reconcile_payment_attempt
- process_refund_update
- expire_seat_holds
- issue_or_refresh_ticket
- process_notification_outbox
- retention_cleanup

These must not be callable as arbitrary privileged operations by an ordinary client. Provider callbacks require signature verification and replay/duplicate protection.

11.12 Realtime policy
- Subscribe only to channels the authenticated user is allowed to read.
- Avoid broad public broadcast of passenger identities, seat-holder identities, private booking IDs, or location.
- A seat-change event may say that a seat availability view should refresh, but the client must query authoritative availability before selecting/holding.
- Handle reconnect by resubscribing and then fetching a fresh snapshot.
- If realtime is unavailable, the app must still function using explicit refresh and normal server requests.

11.13 Storage policy
- Default to private buckets for support attachments or other private documents.
- Set file size/type limits and scan uploaded content where appropriate.
- Validate ownership and authorization before issuing signed URLs.
- Use random object paths, not names/phone numbers as public paths.
- Do not store payment secrets, OTP screenshots, raw QR tokens, or server credentials in public storage.
- Define retention and deletion behavior for every file category.

11.14 Background jobs and reconciliation
- Seat hold expiry: mark/clean expired records, while availability logic independently ignores expired holds.
- Payment reconciliation: query provider/server for attempts left pending/unknown and resolve safely.
- Notification outbox: deliver and retry notifications with bounded retry, dead-letter/needs-review state, and idempotency.
- Refund reconciliation: compare provider refund state with internal record.
- Retention cleanup: remove or anonymize data only according to approved retention policy and legal holds.
- Scheduled task failures must alert authorized operators and be visible in monitoring.
- Jobs must be safe to run more than once.

======================================================================
PART 12 — SECURITY, PRIVACY, AND ABUSE PREVENTION
======================================================================

12.1 Minimum security rules
- TLS for network traffic.
- No privileged secret in the client.
- RLS enabled and tested on exposed data tables.
- Server-side authorization for every protected action.
- Input validation on client and server; server validation is authoritative.
- Rate limits for OTP, support spam, SOS abuse, booking attempts, and other abuse-prone actions, with emergency-use design reviewed carefully.
- Idempotency for booking/payment/cancellation/refund operations.
- Webhook signature validation and duplicate-event protection.
- Secure session storage and appropriate token handling.
- Dependency scanning, code review, and secret scanning in development.
- Production access restricted to named authorized people with least privilege.
- Private logs with redaction and access controls.
- Backup/restore tests and incident response plan.
- Independent security review before real payments or sensitive data go live.

12.2 Threats to test
- Passenger attempts to read another passenger's ticket by changing an ID.
- Passenger attempts to change fare or booking status in a request.
- Client attempts to set its own role to driver/worker/manager/owner.
- Two users attempt to hold the same seat simultaneously.
- A user replays an old payment callback or duplicate webhook.
- A user replays a QR ticket after boarding.
- An expired seat hold is used after the phone clock is changed.
- A client calls a privileged function directly without authorization.
- A public query exposes phone numbers, private notes, location, or payment references.
- Logs or crash reports contain tokens or private QR values.
- A malicious user floods OTP or support endpoints.
- An operator with limited role tries to use owner-only functions.
- A client attempts to bypass cancellation policy by changing local time or request values.
Every item must have a test and a documented expected result.

12.3 Data minimization
- Collect only information needed for booking, safety, support, payment reconciliation, or legal obligations.
- Do not collect continuous location unless there is a defined, approved reason.
- Explain location use at the time permission is requested.
- Restrict trip location to authorized, purpose-limited access.
- Separate normal trip history from SOS/breakdown records as appropriate.
- Avoid logging full phone numbers, payment identifiers beyond what is required, full QR tokens, and private support message contents.
- Define access, retention, deletion, correction, and support processes before launch.

12.4 SOS design
- SOS must be easy to find and usable in a stressful situation.
- Use a deliberate interaction to reduce accidental activation, but do not add a long delay.
- On activation, show “Sending emergency alert…” while contacting the server.
- On confirmed delivery: “Your alert was sent. Follow the on-screen safety guidance.”
- On network unavailable: “We couldn’t send the alert online. Call local emergency services if you are in immediate danger and use the available phone options.”
- Buttons: “Try sending again” -> bounded retry with same event/idempotency key; “Call emergency services” -> only if a verified local emergency number is configured; “Cancel false alarm” -> only under a defined policy and with audit record.
- Never invent local emergency numbers.
- Store only the location/context necessary for the safety event and authorized response.
- Do not promise an operator received the SOS until delivery/acknowledgement is confirmed.
- SOS must have a monitored operational response process before being advertised as a functioning emergency service.

PART 13 — OBSERVABILITY, LOGGING, AND SUPPORT DIAGNOSTICS
======================================================================

13.1 Correlation IDs
- Generate a request/correlation ID for each important server operation.
- Store it with server logs and audit events.
- Show a short support reference to the user only when useful.
- Never use a correlation ID as authentication or as a secret.

13.2 Safe logging
Log:
- Event name, timestamp, app version, safe user/session reference, result status, latency, provider code category, and correlation ID.
Do not log:
- Passwords, OTPs, auth tokens, service-role keys, payment card details, PINs, full provider secrets, raw QR tokens, or unnecessary full passenger details.
- Sanitize user-supplied strings to prevent log injection.
- Restrict log access and set a retention policy.

13.3 Operational metrics
Monitor:
- App launch failures.
- Authentication/OTP success and failure rates.
- Search latency and no-result rate.
- Seat hold success/conflict/expiry rate.
- Booking creation success/failure.
- Payment pending/unknown/failed/succeeded rates.
- Payment-to-booking reconciliation backlog.
- Refund processing latency/failures.
- Ticket issuance failures.
- Notification delivery and retry rates.
- SOS delivery and acknowledgement latency.
- Database CPU/connections/slow queries and function error rates.
- RLS/authorization denials and suspicious access patterns.
Do not expose internal metrics or private incident data to ordinary passengers.

13.4 Support diagnostics button
If “Report a problem” is offered:
- Ask for consent before attaching diagnostics.
- Include app version, device OS version, timestamp, screen category, correlation ID, and sanitized error code.
- Do not automatically attach contact lists, photos, microphone recordings, full location history, tokens, payment credentials, or private ticket QR values.
- Allow the user to describe the issue in plain language.
- Confirm when a support case has actually been created; otherwise explain that it could not be sent.

PART 14 — TESTING MATRIX AND ACCEPTANCE CRITERIA
======================================================================

14.1 UI interaction tests
For every visible control:
- Tap once and verify expected result.
- Tap rapidly several times and verify no duplicate navigation, booking, or payment.
- Use Android Back and verify expected destination.
- Rotate/recreate process where supported and verify safe state restoration.
- Test large font and screen-reader focus.
- Test English and Urdu, including right-to-left layout.
- Test low-end device performance.
- Test disabled/loading/error/success states.
- Verify no clipped labels or overlapping controls.

14.2 Network tests
Simulate:
- Full offline before screen load.
- Connection lost while searching.
- Slow response.
- Request timeout.
- Connection lost immediately after booking submission.
- Connection lost immediately after payment initiation.
- Connection restored after an unknown result.
- Server 4xx validation error.
- Server 401 expired session.
- Server 403 unauthorized action.
- Server 429 rate limit.
- Server 5xx.
- Realtime disconnect/reconnect.
Expected result: clear message, safe recovery action, no duplicate booking/payment, and no false confirmation.

14.3 Booking and seat concurrency tests
- Two users select the same seat simultaneously.
- Same user taps Confirm multiple times.
- Two seats are requested and only one is available.
- Hold expires at the same moment a user confirms.
- A seat is held by one user and queried by another.
- App is killed and reopened after hold creation.
- Phone clock is moved forward/back.
- Segment-based route bookings overlap.
- Segment-based route bookings do not overlap and reuse is allowed only if configured.
Expected result: server-enforced consistency, no overlapping confirmed allocation, accurate error copy, and safe refresh.

14.4 Payment tests
- Provider success.
- Provider definitive failure.
- User cancels provider screen.
- Provider response is delayed.
- App is killed after payment initiation.
- Duplicate webhook.
- Invalid webhook signature.
- Payment success but ticket issuance delayed.
- Payment result unknown after network interruption.
- Payment reconciliation finds a success after client timed out.
Expected result: no double charge caused by blind retries, no false failure/success, and recoverable status.

14.5 Refund/cancellation tests
- Cancellation inside 8-hour boundary.
- Cancellation exactly at 8 hours.
- Cancellation after 8 hours.
- Phone clock manipulation.
- Duplicate cancellation request.
- Refund pending, succeeded, failed, and needs review.
- Booking already boarded or already cancelled.
Expected result: server time and approved policy determine eligibility; UI only displays server result.

14.6 Security tests
- RLS tests for anonymous, passenger A, passenger B, driver, and each operational role.
- Attempts to read or alter another user's records.
- Attempt to set privileged role through profile update.
- Attempt to call privileged server functions without permission.
- Attempt to use a leaked/expired token.
- Attempt to expose private storage file.
- Attempt to replay webhook and QR.
- Confirm no secret appears in APK, frontend bundle, logs, crash reports, or repository.
Expected result: deny by default, no cross-user leakage, no privilege escalation.

14.7 Content consistency tests
Search the app and source strings to ensure:
- No highway fee or toll fee is added or displayed.
- No PKR 500 extra-luggage charge remains.
- No one-standard-bag system or included-luggage counter remains.
- The 10 kg per booked seat notice appears in Help and Privacy Policy.
- The 10 kg notice does not appear in checkout, booking review, payment, or fare summary.
- No fake active route/destination is shown.
- No fake emergency number or support contact is shown.
- No screen says “confirmed” before the server confirms.
- No passenger screen exposes admin or Silent Owner controls.

14.8 Release gate
Do not release to real passengers until:
- Booking and seat concurrency tests pass.
- Payment reconciliation and refund flows are tested with provider sandbox and approved live configuration.
- RLS and authorization tests pass.
- Backup restoration is tested.
- Support/SOS operational response is staffed and verified before SOS is marketed as available.
- English and Urdu copy is reviewed.
- Privacy policy and terms are reviewed by qualified professionals.
- Provider fees, hosting, maps, OTP, payments, storage, and distribution costs are understood and approved.
- Monitoring and incident response are active.
- A rollback plan exists.

PART 15 — OPEN IMPLEMENTATION DECISIONS THAT MUST NOT BE GUESSED
======================================================================

The blueprint is detailed, but these decisions require evidence or explicit business approval before implementation:
- Which OTP/SMS provider is available in Pakistan, its pricing, delivery rates, and supported sender IDs.
- Which payment providers are legally and commercially available, their fees, settlement timelines, webhook behavior, and refund support.
- Whether booking requires sign-in before browsing or only before holding/booking.
- Whether a booking can include multiple passengers and multiple seats.
- Exact fare/tax/legal display requirements after qualified review; current UI rule remains ticket rate only and no separate highway/toll/luggage fee.
- Exact booking horizon, cutoff time, and timetable update process.
- Actual vehicle seat layouts and whether segment-based seat reuse applies to every service type.
- Map provider, map/GPS cost, location accuracy expectations, and offline navigation fallback.
- Actual support channels, working hours, escalation procedures, and languages.
- Exact emergency contact integration and who receives/acknowledges SOS alerts.
- Legal basis, retention, deletion, and data-subject request handling for each personal-data category.
- Production hosting region, backup policy, recovery objectives, and disaster recovery test schedule.
- Exact Supabase plan, usage limits, pricing, region, edge-function capabilities, and current provider guidance.
- Whether a separate custom backend/worker is needed for reliable background jobs and provider integrations.
- App distribution method and verified official update destination.
- Whether notifications use Firebase Cloud Messaging or another supported provider, and associated privacy/configuration requirements.
- Whether analytics/crash reporting is used, and which data fields are excluded.
- Security review of the Silent Owner website and any privileged operational control plane.
- Final legal review of cancellation/refund policy and consumer disclosures.

Never silently turn these open decisions into asserted facts. Record the chosen answer, decision owner, date, rationale, and implementation impact when confirmed.

======================================================================
PART 16 — DEFINITION OF DONE FOR A SCREEN OR FEATURE
======================================================================

A screen/feature is not “done” merely because it looks correct. It is done only when:
1. Every visible button, icon, card, row, switch, and link has documented behavior.
2. Every navigation destination is defined.
3. Every field has validation rules and helpful error copy.
4. Loading, empty, offline, timeout, server-error, permission-denied, and success states are designed where relevant.
5. All network-dependent state is revalidated server-side.
6. Duplicate submissions are handled safely.
7. Access control is enforced server-side.
8. English and Urdu strings are reviewed.
9. Accessibility and low-end-device behavior are tested.
10. Analytics/logging are privacy-safe.
11. Relevant tests pass in staging.
12. No unapproved fees, luggage features, route promises, or security shortcuts remain.
13. Monitoring and support handling exist for failures that could affect real users.
14. Documentation is updated with the actual implemented behavior, not only the intended design.
